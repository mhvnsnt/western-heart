# findings-audit19.txt — DOA4 deep-RE Audit 19 (00dfxxxx lead resolution + recomp cross-check)
# Run: 2026-10-20, headless Ghidra 12.1.4 (Doa4Audit19.java, -noanalysis) +
#      Capstone 5.0.7 PPC disassembly of default_pe.bin + cross-reference against
#      parkerallan/doa4-recomp generated C++ (XenonRecomp output for this XEX).
# Question: what is the 00dfxxxx region that Audits 15-18 chased
# (bl targets 0x00dfd4a8/0x00dfd4c8, branches to 0x00dfd4f8/0x00dfd518)?
#
# === findings ===
# 1. Capstone disassembly at 0x00dfd4a8 (file offset 0x9eeca8 in default_pe.bin):
#      std r20,-0x68(r1) ... std r31,-0x10(r1); stw r12,-8(r1); blr
#      ld  r14,-0x98(r1) ... ld r31,-0x10(r1); lwz r12,-8(r1); mtlr r12; blr
#      mtctr r4; mr r12,r5; bctr        <- import-call trampoline
#    This is the Xbox 360 CRT register save/restore helper block
#    (_savegprlr_20 / _restgprlr_20 and siblings) plus an indirect-call
#    trampoline. It is compiler runtime glue present in every XEX, NOT a
#    game routine and NOT the AFS decrypt function.
# 2. Ghidra Audit19 (this run): the savegprlr prologue pattern fa81ff98
#    (std r20,-0x68(r1)) occurs EXACTLY ONCE in all of .text (0x6e0000-0xf4adff),
#    at 0x00dfd4a8. The region is one contiguous CRT helper block inside .text.
# 3. Why Ghidra 32-bit PPC refused it (Audits 16-17): std/ld are 64-bit
#    encodings; the XDK CRT helpers use them even in 32-bit code (the Xenon
#    CPU is 64-bit). Capstone PPC (either mode) decodes them fine.
# 4. Cross-check in doa4-recomp generated code: the same helpers appear as
#    named intrinsics, e.g. `__savegprlr_28(ctx, base)` called at function
#    prologues (generated/default/dead_or_alive_4_recomp.0.cpp, sub_822F0000).
#    The recomp runtime VA for the sibling helper is 0x82a02df8
#    (RVA 0xa02df8); our block is the RVA 0x9fd4a8 entry of the same cluster.
# 5. CONSEQUENCE FOR AUDITS 12/15: the "prime lead" FUN_00b91ec8 -> 0x00dfd4a8
#    was never a thunk to a decrypt routine. FUN_00b91ec8's body (mflr r12;
#    bl _savegprlr) is a NORMAL function prologue whose first call saves
#    registers. Every conclusion drawn from "the real code is in 00dfxxxx"
#    is retracted: 00dfxxxx is CRT glue, fully identified.
# 6. AFS partition descriptor tables located (static, .data): six parallel
#    28-byte-stride tables in default_pe.bin at file offsets 0xc2b1xx,
#    0xc4a1xx, 0xc4edxx, 0xc508xx, 0xc6cdxx, 0xc6e8xx contain BE pointers to
#    the cache:\*.afs filename strings (chrone 0x8221e9ac, chrtwo 0x8221e988,
#    chrthree 0x8221e964, mot 0x8221e908, snd 0x8221e8ec). Entry shape:
#    {name_ptr, 0, 0, 0, partition_id, runtime_buf_ptr (0x830e....), alt_ptr}.
#    This is the CRI AFS partition table the loader iterates — the code path
#    is table-indirect, which is why 19 audits of string-xref hunting found
#    zero direct references.
#
# === verdict ===
# - The 00dfxxxx lead is CLOSED (identified: XDK CRT save/restore helpers).
# - The keystream/header-cipher routine location is STILL unknown after 19
#   audits. No function in the binary has been shown to derive the 6 per-file
#   4-byte header keys (anm 80b97b52, chrone 7fc2f931, chrtwo 7ff843dc,
#   chrthree fe793a0f, mot 7d40a53e, stg 7d4e3d2e); key reproduction from a
#   derived algorithm: 0/6 by algorithm (the 6 keys themselves are known from
#   the AFS\0 known-plaintext, not from an algorithm).
# - Remaining viable paths (documented, not attempted this run):
#   (a) trace the CRI adxf partition-open path from the .data descriptor
#       tables above (follow runtime_buf_ptr writers in the recomp C++);
#   (b) Ghidra P-code emulation of the adxf open/parse functions once
#       bounded (Audit14 recommendation);
#   (c) cryptanalysis of the 16-byte periodic AFS table cipher directly
#       (the data payload past the header is plaintext — proven by the
#       XPR2 carving + IBUF decoding lanes — so the cipher gates only the
#       AFS TOC / file-boundary metadata, not asset decoding).
