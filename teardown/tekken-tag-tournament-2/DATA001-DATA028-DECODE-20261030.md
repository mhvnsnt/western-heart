## The section-table model (the breakthrough)

Every `0ff512ed` file carries a head table right after its 12-byte header:
BE u32 values, one per 128 KB section of the file (sections sit at file
offsets `k*131072`; section 0's stream starts after the header + table).
Entry `k+1` is section `k`'s decoded output size. The table sums match the
decoded NRFI totals exactly for both files, which is what proves the model:

| file | table entries | stream start (sec 0) | sections | table sum | decoded total |
|---|---|---|---|---|---|
| data001.bin | 2944 | 11788 | 2943 | 851749584 | 851749584 |
| data028.bin | 781 | 3136 | 780 | 120285856 | 120285856 |

Entry 0 is not a section size (data001: magic `0x5042dfe2`; data028:
4244258) and is excluded from the sums.

## The section decoder (tools/ttt2-section-decode)

The stock walker truncates chunks whose blocks total more than 32768 output
and cannot resume a bitstream mid-block, which is why the prefix decode
underproduced by 173,913 bytes across 15 sections and why both files blocked.
The section decoder in `tools/ttt2-section-decode/` fixes this with:

- A bit-exact LZX resume extension on the ReactOS/cabextract decoder
  (`lzx_exact.c`): the next unconsumed bit position is saved at every return
  and restored at entry, so slices resume exactly inside verbatim/aligned
  blocks. Uncompressed blocks resume byte-exact (no bitstream involved).
- Fresh LZX state per section; chunk starts use fresh bits (bit 0).
- Stored-section rule: a section starting with BE u16 0 whose table entry
  equals input length minus 2 is a raw copy (input + 2, no LZX).
- Chunk-done rule: at a block boundary with 16 or fewer bytes of chunk
  input left, the rest is bit padding — the chunk is done. (A real block
  needs at least 17 bytes: 4-byte header + 12-byte R0/R1/R2 + payload.)
- Chunk-start resync: if a chunk's first slice fails, retry its size prefix
  at -1/+1 (the previous chunk's size field overstated by 1 — the data028
  chunk-2383 precedent).
- Block-scan: if a mid-chunk slice fails at a block boundary, scan forward
  up to 32 bytes for the next valid compressed block header (type 1/2,
  length at most 32768, full table validation) and resume there. This
  covers the inter-block gaps (e.g. 4 bytes) that the bit position alone
  does not account for.
- Clamp: a chunk's data never crosses its section end.
- Fallback: binary-search the largest succeeding output length for a final
  partial block, then continue (no early chunk exit).

  sha256 `91286d6b6f4e44b3d104f969f63acb70cc6ac9fcdee490abc4a7fad45227395d`.

  sha256 `838fcbefd640c8faac5d4702a8c907f78400670956cf55971365616b9cf473a7`.

## Reproduce

Pull the sources from release `ttt2-7z-v1` (no binaries committed):

    python3 tools/ttt2_virtual_god.py --pull

Build and run the section decoder (see `tools/ttt2-section-decode/README.md`):

    gcc -O2 -o batchdec3 tools/ttt2-section-decode/batchdec3.c
    ./batchdec3 pulls/data001.bin decoded-data001.bin batchdec-data001.log 2944 11788
    ./batchdec3 pulls/data028.bin decoded-data028.bin batchdec-data028.log 781 3136

Verify: each log line reads `EXACT` (or `STORED`); the decoded totals equal
the table sums above; the NRFI boxes tile to EOF as listed.

## Dead ends recorded (do not repeat blindly)

- The `chain001` verbatim tail for data001 (179,896,320 B, 5,490 blocks of
  32768) is suspect and underproduced by 212,006,161 B against the corrected
  tail total; do not use it. It came from a spurious uncompressed parse at
  205783042 (an 8,440,655-byte block whose follower has no valid header;
  its pretree Kraft sum is 0.709, not 1.0).
- Scanning chunk-table lengths from arbitrary starts proves nothing on
  random data (u16 sizes are valid with probability ~65534/65536 per step).
  Decode success plus table-entry totals are the validators.
- The data028 gap was not a stored/uncompressed region and not a corrupt
  pull: it was walker drift (1-byte size overstatement) plus inter-block
  gaps. The section decoder above is the fix.
