## Phase 1 — Oodle decompression

Three ranked options:

**Option A (recommended):** Call the game's own `oo2core_*.dll` via FFI (`OodleLZ_Decompress`) — same thing the game does, zero code-copying exposure. Established community pattern: UnPSARC does exactly this with `oo2core_9_win64.dll`; repak's `oodle_loader` is the FFI reference implementation. Python `ctypes` prototype planned.

**Option B:** `zao/ooz` (`libooz`) — open Kraken/Leviathan/LZNA decoder with `Ooz_Decompress` entry matching the Oodle signature. CMake-built, Python CFFI bindings. License unverified — anything derived stays PRIVATE until the LICENSE file is read.

**Option C:** `rarten/ooz` (2019, "educational use only") — cross-validator only.

**Exit criterion:** byte-identical decompression two ways.

## Phase 2 — `.pac` format

Publicly established facts to verify:
- 64-bit ID addressing (e.g. `D2ACC42D89D89FFD`)
- Nested pacs (`audience.pac` → `0000.pac` → `.bpe` → DDS)
- `string_win.pac` string tables
- Character folders `\pac\ch` / `\pac\edit\ch`
- Oracle tools: CakeTools, rePac/PAC Editor, WrestleMinus, CakeHook `_mods`

**RE procedure:** hexdump headers → hypothesize entry structs → validate by extracting and checking magic bytes → diff against oracle output.

## Phase 3 — `.ch.pac` (character)

3. Skeleton via bone-name strings + cross-character diff
4. Animations via frame-count/track headers
