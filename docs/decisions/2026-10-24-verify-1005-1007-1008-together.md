## Interaction simulations (custom script, 7/7 PASS)

Run against the real Pantera moveset + King bank on main, through the real
`_attackClipPlan`, `_rootMotionApply`, `_physics`, `getHitbox`, `moveReach` /
`inReach` code. Button names per owner directive: LP1 = Tekken 1, RP2 = Tekken 2,
LK3 = Tekken 3, RK4 = Tekken 4.

- (a) Root motion + hit detection: RP2 (reach 1.75 m) against a defender at 2.50 m
  whiffs from the start position and CONNECTS after +0.847 m of travel (gap 1.65 m).
  Contact is resolved at the travelled position because `game.js` `_update` runs
  both fighters' `update()` (which runs `_physics` → `_rootMotionApply`) before
  `_resolveCombat` in the same tick, and `getHitbox` bone positions come from
  `getWorldPosition`, which reflects the new root position. In `_physics`,
  root motion is applied BEFORE the arena clamp and the body-vs-body pushout in
  the same call, so walls/opponents resolve against travel the same frame.
  Pushout probe: attacker RP2-travelling into a defender at 1.0 m ends at gap
  1.467 m, minimum gap exactly 1.450 m (the ground pushbox width), never crossed.
- (b) Strings + root motion: string step 2 starts exactly where step 1 ended
  (no snap-back) and travel is never double-counted — verified with a travelling
  first hit too: RP2 (0.847 m) then the 2,1 step (solo 3.245 m) ends at exactly
  0.847 + 3.245 = 4.092 m. `_rootMotionApply` re-anchors its cursor on a new
  plan id/name and never resets `root.position`.
- (c) Strings + hit detection: the step-2 hitbox is the step-2 move's own —
  for 1,2 it is limb armR (RP2), damage 20, reach 2.05, move object `1,2` itself,
  not step 1's LP1 (armL, runtime damage 9 via slot `1~t8.king`).
- (d) Whiff travel: whiffed RP2 travels exactly 0.8470 m, same as on hit.
  `_rootMotionApply` never reads `hasHit`.
- (e) Block/hitstun: root motion runs ONLY in `attack` / `vskill` / `vreversal`.
  Verified off in block, hitstun, knockdown, sidestep, dodge, jump, crouch,
  idle, throwExec, thrownExec, walk; on in vskill and vreversal.
- (f) Strings data: `3+4,LP1` resolves through the slots alias `3+4,1 → JGS.1`
  with damage 28, limb armL. The PR #1007 record `string_fix_20261024` on main
  lists exactly 54 `damage_fixed_keys` and 9 new slot aliases; `1,2` step-2
  damage 20 is documented as already MOD-correct.

## Gaps and observations (no fix attempted — nothing here is a regression)

1. The 200 ms post-move string grace window has NO suite test referencing
   `_stringGraceUntil`. Code-verified only: `_tickState` sets it to now + 200 ms
   when a non-grab attack completes, it is cleared on hitstun / knockdown / KO,
   and `_tryAttackFresh` only chains through it when the fighter can act, the
   notation is a single button, and the continuation resolves. Recommend a
   regression test for the grace window.
2. Observation, bank data (not an interaction bug): the `2,1` step-2 clip
   (row:220, 85 stream frames) carries 3.245 m of decoded `root_t` travel.
   PR #1008 applies `root_t` verbatim by design, so this is a data eye-check
   for the owner, not something to "fix" by inventing a distance.
3. LP1 runtime damage is 9 (slot `1~t8.king`), while the shadowed T3 record
   `1` carries 11. This is the documented PR #1007 behaviour ("singles that
   fire via slots use MOD damage"; T3 records left as source records), not a
   regression.
