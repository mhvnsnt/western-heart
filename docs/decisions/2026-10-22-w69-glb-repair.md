# Decision: 165 triangulated DOA4 GLB header repair (worker 69, 2026-10-22)

## Owner instruction (verbatim quote)
"Repair the 165 GLBs with the fixed writer in `tools/doa4_decode3.py` (TEXCOORD_0 byteOffset bug)."

## The bug (from SWEEP-AUDIT-2026-10-20 finding 1)
`tools/doa4_decode.py:write_glb` declared the TEXCOORD_0 accessor with
`byteOffset = n*12`, but the BIN chunk is interleaved (pos 12B + uv 8B per
vertex, stride 20), so the correct byteOffset is 12. Every triangulated GLB
failed strict importers — Blender: "buffer is smaller than requested size".
The fixed writer (`tools/doa4_decode3.py:write_glb_fixed`) uses byteOffset 12.

## Method actually used
Surgical header patch, NOT a full re-decode (the chr*.afs sources are gone
from the VM until the ISO reassembly completes). New script
`~/workspace/w59/glb-header-repair.mjs` mirrors `write_glb_fixed` exactly:
1. TEXCOORD_0 byteOffset n*12 -> 12 (the named bug).
2. POSITION min/max recomputed from the actual vertex data — the old writer
   emitted bare `NaN` tokens (Python json) in some files, which is invalid
   JSON and kills strict readers independently of the byteOffset bug.
3. `asset.generator` -> `doa4-decode3` (header now conforms to the fixed writer).
BIN chunk (geometry) is copied verbatim — byte-identical in all 165 files.

## Proof
- Dry run: 165/165 pass a strict accessor-bounds check
  (`byteOffset + (count-1)*stride + size <= bufferView.byteLength` — the same
  check Blender's `decode_accessor` performs), 495 header changes, 0 failures.
- Scratch-copy test: BIN region byte-identical before/after; new header parses
  as strict JSON; uv byteOffset 12; min/max all finite.
- Post-repair spot check vs git HEAD: BIN chunks identical
  (chrone_00, chrtwo_25 confirmed).
- Commit `63ee49a`: exactly the 165 GLB files modified, 0 other files touched.

## Deviations

rewritten by this lane") — this lane's owner task explicitly orders the
repair, which is the authorization.
